# aqs-cpp 性能评估报告

日期：2026-08-27　版本：0.1.0　基准工具：`tests/bench_aqs.cpp`

## 1. 环境与方法

| 项       | 值                                                  |
| -------- | --------------------------------------------------- |
| CPU      | AMD Ryzen 9 9950X3D（16C/32T，~5.7GHz）             |
| 系统     | Linux                                               |
| 编译     | g++ -O2（CMake 默认 RelWithDebInfo），-Wall -Wextra |
| 绑核     | `taskset -c 0-15` 限定单个 CCD                      |
| 对比对象 | `std::mutex`、POSIX `sem_t`（同进程同负载）         |

复现命令：

```bash
cmake --build build -j$(nproc)
taskset -c 0-15 ./build/bench_aqs
```

**方法学要点（两处测量陷阱的修正过程保留在此备查）：**

1. **空临界区失真**：临界区为空时，持锁线程会在自己的时间片内批量排空循环，
   测得的是"时间片独占"而非真实竞争（mutex 在 T=2 曾虚高至 49M ops/s，
   交接延迟曾出现物理上不可能的 24ns）。修正：临界区加入约 0.2µs
   确定性忙等工作（12 次 `pause` 指令），逼出真实交接。
2. **naive ping-pong 失真**：双线程互抢不构成严格交替。修正：锁保护的
   baton 强制逐次移交，每次持锁对应一次真实的"唤醒对端→交接完成"。
3. 轻量配置取 3 次采样最小值；重度竞争单样（噪声远大于采样偏差）；
   并行段以 go 标志对齐起跑线。

## 2. 评估中定位并修复的框架缺陷

### 2.1 丢失无竞争快速路径（已修复）

首跑无竞争成本达 28ns/op，排查发现移植丢失了 OpenJDK 的"先试钩子后入队"结构：

```java
// OpenJDK acquire(int arg)
if (!tryAcquire(arg) && acquireQueued(addWaiter(Node.EXCLUSIVE), arg)) selfInterrupt();
```

原实现 `acquire_queued(add_waiter(mode::exclusive), arg)` 无条件建节点入队——
每次获取都付出 arena 互斥堆分配的全款。已按 JDK 原义补回四个入口
（`acquire / acquire_for / acquire_shared / acquire_shared_for`）：
先试钩子，失败才排队；快速成功不欠传播（此时队列必空，语义安全；
公平模式的钩子自带 `has_queued_predecessors` 门，插队不会越过已排队者）。

效果：无竞争路径 **28ns → 6-7ns，约 4 倍改善**。

### 2.2 bounded_queue 测试终止协议缺陷（顺带暴露并修复）

快速路径改变时序后，有界队列测试一度确定性挂死。根因是测试自身的退出判据：
消费者以 `consumed >= produced` 判定完工退出——当生产者阻塞在
`not_full.await()` 尚未完成推送时二者恰好相等，消费者集体提前退场，
滞留生产者永眠于条件队列。旧代码下每次持锁均走队列、唤醒链均匀，
该窗口从未命中；属潜伏缺陷被时序变化暴露，非库语义问题。

修复：改用算术守恒闸门——弹出值为全局唯一序列（1..N），仅当
`队列空 && 弹出总和 == 期望总和` 时退出；能弹满即证明所有生产者已完工。
见 `tests/test_aqs.cpp` 中 `test_bounded_queue_with_condition` 注释。

## 3. 基准数据

### 3.1 无竞争单线程成本（3'000'000 次 lock+unlock，3 样取最小）

| 实现         | ns/op | 相对 mutex |
| ------------ | ----- | ---------- |
| aqs 非公平锁 | 6-7   | ~290%      |
| aqs 公平锁   | 6     | ~290%      |
| std::mutex   | 2     | 100%       |

- 公平锁与非公平同价：无竞争时公平门查不到排队者即放行。
- mutex 的 2ns 为全缓存驻留的理想下界。
- aqs 剩余开销 = 虚调用 + 状态 acquire 读 + CAS + owner 写（可重入记账），
  属 Java 对等语义的结构性成本。

### 3.2 有竞争吞吐（ops/s，临界区含 ~0.2µs 忙等工作）

| 线程 | aqs 非公平 | aqs 公平 | std::mutex |
| ---- | ---------- | -------- | ---------- |
| T=1  | 6.9M       | 6.9M     | 7.0M       |
| T=2  | 3.65M      | 3.50M    | **4.04M**  |
| T=4  | **4.03M**  | 3.92M    | 3.06M      |
| T=8  | **4.36M**  | 4.02M    | 3.11M      |

- T≥4 后 aqs 反超约 +30% 并持续拉开：AQS 队列纪律压制 futex 惊群，
  高核数下优势随线程数扩大。
- 公平锁代价仅 5-8%（防饥饿换来的合理折损）。
- T=2 落后于 mutex 约 10%，属交接延迟劣势的传导（§3.3）。

### 3.3 交接延迟（严格交替 100'000 次移交）

| 实现         | ns/次（多轮区间） |
| ------------ | ----------------- |
| std::mutex   | 103 - 194         |
| aqs 非公平锁 | 282 - 450         |

裸 futex 快 1.5-2.5 倍。差距为 AQS 队列协议的结构性成本：
一次排队需 enq 两次 CAS + arena 分配 + SIGNAL 标记 + 主动 unpark；
glibc 仅 FUTEX_WAIT/WAKE 两声 syscall。

区间波动大源于线程落点跨 CCD/同 CCD 随机，属拓扑噪声，
评估结论取区间而非单点。

**选型推论**：双线程乒乓交替模式 → 选 std::mutex；
多客户端争抢共享资源 → 选 aqs 锁。

### 3.4 共享模式信号量（T=8 抢占，ops/s）

| 实现                         | 吞吐                      |
| ---------------------------- | ------------------------- |
| POSIX sem_t(1)               | 3.10M                     |
| aqs::semaphore(1)            | **3.88M（+25%）**         |
| aqs::semaphore(3) 多许可并行 | **17.8M ≈ 单许可 4.6 倍** |

`setHeadAndPropagate`/`doReleaseShared` 级联传播的价值得到量化验证：
多许可下吞吐近线性放大；单许可争抢下共享队列协议的开销被传播收益覆盖，
反超 POSIX 原生实现。

## 4. 结论与建议

| 维度         | 评价 | 依据                                           |
| ------------ | ---- | ---------------------------------------------- |
| 无竞争路径   | 优秀 | 个位数 ns/op，Java 语义完整保留                |
| 中高并发吞吐 | 强   | ≥4 线程稳定领先原生 mutex 30%+                 |
| 极限交接延迟 | 中   | 比裸 futex 慢 1.5-2.5×，正确性与公平性的协议税 |
| 共享传播     | 很强 | 近线性扩展，胜 POSIX sem_t                     |

**未动用的优化杠杆**（源码内 ponytail 注释已备案，当前数据未显示必要）：

1. 全链 seq_cst 逐点降级 acquire/release（`src/aqs.hpp` 尾注释）；
2. 竞争入队的节点分配带全局互斥（`new_node`），可换无锁 freelist，
   预计回收交接路径上约 40-80ns（§3.3 差距的一部分）。

两项均留待实测瓶颈出现后再启用，避免提前复杂化。
